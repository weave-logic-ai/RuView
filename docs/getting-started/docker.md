# Run the sensing server in Docker

This page runs the `sensing-server` from the published image. For the same
flow without containers, and for flashing and provisioning the board, see
[quickstart-esp32-s3.md](quickstart-esp32-s3.md). Provision your node with
`--target-ip <host-ip>` and `--target-port 5005` as shown there.

Image: `ruvnet/wifi-densepose:latest` (as of 2026-10-01 this is `sha-b90b592`; Docker Hub; also on
`ghcr.io/ruvnet/wifi-densepose`). It is built for amd64 and arm64. Do not use
the `:python` tag; it runs the retired v1 pipeline.

## Two things the plain `docker run` misses

A bare `docker run -p 3000:3000 ruvnet/wifi-densepose:latest` does not work
with the current entrypoint, for two reasons.

1. **Auth is required.** The container exits with code 64 unless you set
   `RUVIEW_API_TOKEN` or explicitly opt out with
   `RUVIEW_ALLOW_UNAUTHENTICATED=1`.
2. **UDP needs a source guard.** The server inside the container binds its UDP
   port to `127.0.0.1` unless you give it a guard. Set `RUVIEW_UDP_ALLOW` to the
   node IP or CIDR (preferred), or `RUVIEW_UDP_INSECURE_LAN=true` to accept the
   spoofing risk. The entrypoint then binds UDP to `0.0.0.0` for you; set
   `RUVIEW_UDP_BIND` only to override that.

The server reads `RUVIEW_UDP_BIND`, `RUVIEW_UDP_ALLOW` and
`RUVIEW_UDP_INSECURE_LAN` from the environment, so you set them with `-e`, as
shown below.

## Try it without hardware (simulated demo)

To see the dashboard with no board, run this. It is for loopback or lab use
only: it turns auth off, so do not publish the ports beyond `127.0.0.1` and do
not run it on a shared network.

```bash
docker run --rm --name ruview-demo \
  -p 127.0.0.1:3000:3000 \
  -p 127.0.0.1:3001:3001 \
  -e RUVIEW_ALLOW_UNAUTHENTICATED=1 \
  -e CSI_SOURCE=simulated \
  ruvnet/wifi-densepose:latest
```

Open <http://localhost:3000/ui/>. Everything on screen is SYNTHETIC data
generated by the server. It exercises the pipeline but is not sensing. No UDP
settings are needed because no board is sending frames.

## Run it with a board


First find the address your board's frames will appear to come from.

On macOS, OrbStack rewrites the sender address of incoming UDP to the bridge
gateway, so the container never sees the board's own address (measured on
OrbStack, image `b90b592d`; Docker Desktop is untested and may behave the
same). Allow the gateway instead:

```bash
docker network inspect bridge --format '{{(index .IPAM.Config 0).Gateway}}'
```

Call the result `<docker-gateway-ip>`. On Linux the board's real address is
expected to be preserved, so you would allow `<node-ip>/32` or your network
range. Linux is not yet tested.

```bash
export RUVIEW_API_TOKEN="$(openssl rand -hex 24)"
echo "$RUVIEW_API_TOKEN"   # keep this, you enter it in the UI

docker run --rm --name ruview \
  -p 127.0.0.1:3000:3000 \
  -p 127.0.0.1:3001:3001 \
  -p 5005:5005/udp \
  -e RUVIEW_API_TOKEN \
  -e CSI_SOURCE=esp32 \
  -e RUVIEW_UDP_BIND=0.0.0.0 \
  -e RUVIEW_UDP_ALLOW=<docker-gateway-ip>/32 \
  ruvnet/wifi-densepose:latest
```

- Ports: 3000 is the dashboard and API, 3001 is the sensing WebSocket and
  5005/udp receives frames from the board.
- `CSI_SOURCE=esp32` makes the server listen for the board. Set it
  explicitly.
- `RUVIEW_UDP_ALLOW` takes one or more addresses or ranges in CIDR form.
  Using your LAN range here on macOS drops every frame.
- Instead of the allowlist you can use `-e RUVIEW_UDP_INSECURE_LAN=true`.
  This accepts frames from any address, so use it only on a network you
  trust. Write `true`, not `1`: the value `1` makes the server exit with an argument error.
- Even with an allowlist, the UDP stream is unauthenticated. The allowlist
  only filters by sender address.
- With `CSI_SOURCE=auto` (the image default) the server shows data tagged
  `simulated` until a real frame arrives. Simulated output is not sensing.

## Open the dashboard

Open <http://localhost:3000/ui/>. Use `localhost`. The container validates
the Host header, so opening the page through `http://<host-ip>:3000` from
another machine gets `421 Misdirected Request`. To allow it, publish the
port beyond loopback (drop `127.0.0.1:` from the `-p 3000:3000` and
`-p 3001:3001` options) and add `-e SENSING_ALLOWED_HOSTS=<host-ip>`. The
token is still required.

Open QuickSettings, find **API Access**, paste the token and click
**Save & Apply**.

## Check that it is working

```bash
curl -s -H "Authorization: Bearer $RUVIEW_API_TOKEN" \
  http://localhost:3000/api/v1/status
```

Status alone cannot tell "never connected" from "working". With
`CSI_SOURCE=esp32` it reports `"source": "esp32"` and a `source_state` of
`live_unverified` even before the first frame. `esp32:offline` or
`disconnected` appears only after frames arrived and then stopped. Use
`/api/v1/nodes` (same `curl` form, port 3000) as the real check. Call it
twice, a few seconds apart. An empty list (`"nodes":[]`) means no frames have
arrived. Your node should show `csi_status` of `active` and a `csi_sequence`
that grows. Growth per second is an upper bound on the rate received. Then read
[whats-real.md](whats-real.md) for what the numbers mean.

## docker compose

`docker/docker-compose.yml` as shipped does not start the sensing server: it
sets neither a token nor the unauthenticated opt-in, so the container exits
with code 64, and it sets no UDP bind. It also defines a second service on
ports 8765 and 8080. Until the file is fixed, use the `docker run` command
above, or add the environment variables from that command to the compose
service. Both `docker run` without a token and the shipped compose service
exit with code 64 (measured).

## Troubleshooting

See [troubleshooting.md](troubleshooting.md). The most common cause of "the
server is up but there is no data" in Docker is the UDP bind or allowlist
above.
